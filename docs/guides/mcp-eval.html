Letting an assistant run Octave: devtools.mcpEval

Guide · 23 September 2026

devtools.mcpEval is devtools.mcp plus two tools that run code: octave_eval and octave_test. It is a separate server on purpose, with its own command and its own name in your assistant's configuration, so that the permission you give the read-only one never reaches this one. Read the section on what contains it before you configure it.

What it adds

ToolAnswers
octave_evalwhat running some Octave code produces, in a workspace that persists between calls
octave_testhow many of a function's built-in tests pass, and what failed

The five read-only tools of devtools.mcp are served as well.

Configure it under its own name

{
  "mcpServers": {
    "octave-eval": {
      "command": "octave-cli",
      "args": ["-q", "--no-init-file", "--eval", "pkg load devtools; devtools.mcpEval ()"]
    }
  }
}

Configuring it beside the read-only server is fine and is the intended setup: the assistant gets a set of tools it may use freely under octave, and one it must ask about under octave-eval. The rules of the read-only server apply unchanged: do not shorten the command, name octave-cli.exe in full on Windows, and load the packages you want it to see. See the read-only guide for why.

Workspaces

Code runs in a workspace named by an opaque handle. Every call names one: new opens a workspace and the reply gives its handle, and passing the handle back continues it. Variables persist, clear works, and two workspaces cannot see each other.

The handle is required. An assistant that leaves out an argument is the ordinary case, and a missing handle taken to mean "start clean" would lose a workspace without a word. Eight workspaces live at once and the oldest is dropped; a call naming one that is gone gets an error that says so.

octave_test takes no workspace. Tests run in a context of their own every time, so a result cannot depend on what was evaluated before. It resolves the name through which and runs the file, which is what lets it test a namespaced function or a class method.

The deadline

An evaluation still running after twenty seconds is stopped, and the reply says so. What the code assigned before it was stopped is still in the workspace, and what it printed is still returned. Where your work honestly takes longer, raise it, up to six hundred seconds, in the server's configuration:

"env": { "DEVTOOLS_EVAL_SECONDS": "120" }

It is not a tool argument: that would cost tokens in every request, and it is your decision rather than the assistant's.

The deadline does not recover everything. A call stuck inside one long compiled routine, or blocked waiting on input, never reaches a point where the interrupt can be noticed; then only restarting the server helps.

What contains it, and what does not

What evaluated code prints is captured at the file descriptors and comes back in the reply, never into the stream that carries the protocol. That includes what a subprocess prints and what a warning writes, in the order it was written. input and keyboard are disabled while a call runs, since there is no terminal for them to read from.

None of this is a sandbox. Evaluated code can read and write your files, use the network and use memory exactly as any code in your Octave can. The containment keeps the protocol intact and gets the server back when code does not return; it does not defend against code that means harm. Configure this server only where that is acceptable.

Without a compiler

The package installs without a C++ compiler, and this server still works, with two guarantees weaker: there is no deadline, and a subprocess's output is contained by name rather than at the descriptor. system still runs, its output taken back and printed through the interpreter, so ordinary code is unaffected. What is refused is popen opened for writing and an asynchronous system, whose output cannot be taken back at all.

Check the setup

devtools.selftest (), run with no argument, checks this server as well as the read-only one: that it starts, answers in both protocol versions, and keeps standard output clean while it runs code, including a call that starts a subprocess and one that never returns.
